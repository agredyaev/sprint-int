# GitHub Pages publication — Quick-generated Parquet, zero-install CI

Only run this stage after the **real** independent classification review, full
`sharpwriter` Quality Gate and `publication_gate.json.pass=true`. Never invent
receipts: the five `quality` flags attest preceding checks but do not execute
those skills.

## Canonical contract

- **Temporary and outside Git:** raw Jira/Confluence source material, review
  workspaces, approved concise JSON transfer, validation receipts.
- **Canonical in Git:** `data/sprints/<ID>.parquet` — one allowlisted approved
  Reporting sprint per immutable ID, typed numeric metrics, concise narrative.
- **Derived in Git:** `data/history.parquet` — one scalar row per sprint, rebuilt
  by Quick from all canonical snapshots. This is not another source of truth.
- **Consistency seal in Git:** `data/manifest.json` — expected Parquet IDs/versions, SHA-256 and sizes; regenerated by Quick; not a report source.
- **Published by CI unchanged:** allowlisted static assets, `data/manifest.json`, `data/history.parquet`,
  `data/sprints/*.parquet`. No `.py`, `.json` reporting snapshots, private review
  files, shell scripts or quality receipts are published.
- **Not hosted on Pages:** compressed `artifacts/sprint-history.tar.gz`, attached
  as a GitHub Actions workflow artifact with a bounded retention period.

DuckDB-Wasm executes in the reader's browser. It loads `history.parquet` first
and fetches only the selected sprint's Parquet details. No SQL backend, Python,
Go, `uv` or DuckDB installations run in GitHub Actions.

For any new Parquet field, follow `docs/SCHEMA-EVOLUTION.md` inside this installed skill before creating the next snapshot. Quick must increment the schema version, update the history reader and test old/new files. CI does not migrate data.

## Exact handoff

1. Construct only the approved allowlisted JSON (`examples/quick-payload.json`
   shape) with stable sprint ID, real ownership checks and complete evidence.
2. Verify security approval for the target GitHub Pages audience. If absent,
   do not publish; preserve a local draft outside Git.
3. Quick writes and reads back `data/sprints/<ID>.parquet`. The optional helper
   `skills/sprint-intelligence/scripts/pages/export.py` can be called **inside
   Amazon Quick's environment**, where Python + DuckDB are available:

   ```sh
   python skills/sprint-intelligence/scripts/pages/export.py \
     --input "$RUN/approved-sprint.json" \
     --publication-gate "$RUN/out/publication_gate.json" \
     --quality "$RUN/out/quality.json" \
     --selection "$RUN/out/highlight_selection.json" \
     --report "$RUN/report.md" \
     --manifest "$RUN/report-manifest.json" \
     --receipt "$RUN/sharpwriter-receipt.json" \
     --repo /path/to/sprint-intelligence-pages
   ```

   It enforces allowlists, refuses silent overwrite, checks round-trip, and
   prepares the snapshot/index/manifest together and commits the manifest last. If Quick writes Parquet natively instead, it
   must implement the same checks and schema. Never run this in CI.
4. Commit the approved sprint Parquet, regenerated `history.parquet` **and** Quick-generated `manifest.json`.
5. GitHub Actions runs shell/JS checks, stages static files and releases a
   tar.gz backup. Parquet semantic validation is **Quick's** responsibility.
6. Opening the Pages site loads DuckDB-Wasm automatically. No client installs.

A new repo intentionally has no binary Parquet before Quick first exports a
snapshot; the workflow refuses to publish an empty data set. Production must
never mix synthetic and real report files. Pages being backed by a private
repository does not guarantee private access to downloadable asset URLs.
